## 1. 工作原则与审核门槛

先确定接口和状态语义，再实现持久化、算法、异步、检索，最后做并发/恢复验证和交付。每阶段保留可解释的小变更，测试通过且人工核对后才提交；不为了展示历史而最后拆分或伪造时间。实现中的新规则先补充文档，不能静默改变审核结论。

设计和 P1 已经通过用户审核；P2、P3 按新的阶段授权依次实现、验证和提交。未来提交节点仍需对应实际完成阶段。

## 3. 各阶段详细交付与测试

### P0：需求与设计审核（已通过并提交）

- 核对附件全部 3 页；把强制要求、加分项、用户边界和默认建议分开。
- 确认文档列表/详情、按文档查询任务、元数据统计这些容易遗漏的功能已覆盖。
- 把 CPU 耗时与提交异步、数据库真相与调度队列、任务状态与失效状态分别说明。
- 原设计轮不创建工程；本轮设计提交后，P1 创建 pom.xml、Java 基础结构、schema.sql 和持久化测试。
- 先提交修订设计；不为最终“AI 对话记录”伪造未发生的对话或截图。

### P1：工程、DDL、校验与错误契约

交付：可启动的基础服务、固定依赖版本、配置说明、持久化模型、公共响应 DTO、统一异常映射。schema.sql 为建表真相，Hibernate validate 校验；固定数据库路径可配置。

测试方式：

1. `mvn test` 验证基础校验和映射；先确定 Jackson 严格类型/未知字段行为，避免“字符串 3 自动变数字”偏离契约。
2. 使用临时文件目录启动，确认自动建表和索引；第二次启动不清表、不覆盖数据。映射不匹配必须启动失败，不能自动改旧 schema。
3. 原文 CLOB、UUID、Instant/时区、VARBINARY 通过真实 H2 往返；测试空字符串不是 null，中文渠道及长度/首尾空白规则与契约一致。
4. 构造违反唯一键、FK、CHECK 的写入，验证数据库兜底行为；主键冲突需映射 409，而不是笼统 500。
5. 启动配置核对：Java 17、文件 JDBC URL、SQL 初始化先于 JPA validate，Open Session in View 关闭。

完成条件：持久化与接口基础契约可解释，但不能声称异步业务已经可用。保存首次可重复启动的真实终端输出。

### P2：算法模块

交付：无数据库依赖的向量和相似度模块、编解码模块、固定容量 Top-K、CPU 模拟，以及 charhash-v1 规则说明。

测试方式：

- 空串、中文、ASCII、emoji、重复字符、换行、纯空白、最大长度；拒绝孤立代理项。
- 相同文本多次和并行调用，编码后逐字节相同；不同 ID/渠道不影响向量；在独立 Java 进程间复核黄金样例，不能只写“约等于”。
- 黄金样例包含人工可核对的特征列表/桶编号，避免用同一生产实现生成期望值再自我验证。
- 二进制长度 1,024、大端编码已知 float 样例、序列化往返；长度错误、未知版本、NaN/Infinity 被拒绝。
- 余弦以手工向量验证：同向、正交、零向量；使用明确数值误差界。另用词面相近样例作展示，不能当真实语义评测。
- 多组固定随机种子的候选分数与 ID，把堆结果对照完整排序；覆盖同分、逆序输入、K=1、K=N、K>N、空集。
- CPU 模拟确实消耗 CPU，支持中断；不以“必须耗时 X 毫秒”写不稳定单测。

完成条件：能不看代码复述 token 编码、桶碰撞、归一化、零向量定义和堆比较器。

### P3：异步提交、任务状态和持久化恢复

交付：POST /documents，GET /tasks/{taskId}，GET /documents、/{documentId}、/{documentId}/task；队列/调度/worker 生命周期；条件领取、成功原子发布、失败记录；启动恢复。

测试方式：

1. 用闩锁控制 Vectorizer，使后台阻塞，断言提交仍返回任务 ID；不要用提交延迟与电脑速度绑定的脆弱阈值。
2. 分别观察 QUEUED/RUNNING/SUCCEEDED/FAILED；完成带文档、失败带安全错误，原文/渠道/时间准确。
3. 同 ID 多线程提交，恰好一对文档/任务；不同 ID 同文本允许建多个独立文档。
4. 同一个 taskId 重复投递，只有一次条件领取成功、attemptCount 正确，只有一次成功发布。
5. 测试配置 queueCapacity=1、workerCount=1；暂停消费者、压满队列，确认已入库任务等待补扫并最终完成；积压上限拒收不留记录。
6. 注入“事务已提交但提交后唤醒失败”；周期补扫必须仍可处理。扫描前页 ID 全被去重时，后页未调度任务不能永久饥饿。
7. scheduledIds 的 add/remove/size/快照/clear 均使用同一 monitor；停机 join 后才能 clear；锁内不访问数据库/做 CPU 工作，配合队列并发测试核对生命周期。
8. 基础重启恢复：准备 QUEUED/RUNNING/SUCCEEDED/FAILED，重启后只恢复未完成；已执行三次的 RUNNING 失败终止。
9. 数据库已确认回滚的临时冲突有限重试；持续不可用降级探测；提交不明按 taskId/attemptCount 核对；事务重试不增加向量执行次数。
10. 检查工作线程数固定；异常任务之后其他任务仍能执行；关闭期间不再接收新任务。

完成条件：能解释“为何 202 时队列可能还没有任务”和“为什么内存去重不等于数据库执行权”。

### P4：检索、失效和统计闭环

交付：POST /search、PUT /documents/{documentId}/invalidation；读写锁封装、批量候选扫描、Top-K 计数、完整 API 示例。

测试方式：

1. 固定语料包含两个渠道、default 渠道、未完成、失败、失效、空文本；检索仅取合法候选，渠道过滤在 Top-K 前执行。
2. 同分 ID 升序；空查询按约定返回零分 Top-K 并计数；不足 K、空库和非法 K。
3. 文档在排队/处理/完成时失效；之后任务完成不覆盖标记，invalidatedAt 首次写入后不变。
4. 每次只给最终返回项 +1；扫描过但未选中的文档不变；一个失败计数事务所有文档都不变。
5. 请求与响应字段完整；任务查询和文档详情在成功发布后自洽；列表包含失效和失败记录并支持设计的过滤/分页。
6. 暂停某次搜索持读锁，失效须等待；放行搜索并计数后失效成功。另测试失效先成功，随后搜索绝不返回该文档。
7. 数据损坏/不支持版本返回可诊断 500，不能把候选静默删掉当正常成功。
8. 查询向量化、扫描、计数阶段分别触发整体预算/取消，验证事务回滚（提交前）、读锁与许可释放；提交已成功或结果不明时不虚报回滚、不重复计数。

完成条件：可演示“提交→异步完成→检索命中→计数增加→失效→后续检索排除”的完整闭环。

### P5：核心验收优先，增强验证后置

**P5-A 核心验收（必做）**：P3/P4 业务闭环优先可运行；随后确认同 ID 并发唯一、最终 Top-K 原子计数与中途回滚、失效/发布竞争、队列满补投和积压拒收、一次真实进程中断恢复、次数上限边界、中文渠道，以及检索超时/取消最终释放锁和许可。数据库三类故障先用可控替身验证决策，不必先搭建完整故障基础设施。

**P5-B 增强验证（后置，不扩大功能）**：逐个真实崩溃窗口、多轮反复终止进程、长时间压力及更大语料性能观察。仅在核心通过后按风险选择执行；未做项明确记录，不能冒称验证过，也不作为首次交付闭环的前置条件。

下表为完整验证候选，P5-A 对应项目必须覆盖；其余作为 P5-B。交付相应测试及真实运行结果。使用 JUnit、可控闩锁/屏障和测试替身；不通过大量 sleep 猜测线程时序。超时只作为测试卡死保护。测试故障入口只在测试配置可用，不能暴露生产管理后门。

| 故障/竞争 | 注入方式 | 必须观察的结果 |
| --- | --- | --- |
| 并发 Top-K 命中 | 多线程屏障同时开始，记录每次成功结果集合 | 每个文档增量等于所有成功计数事务中包含它的次数，非所有候选次数 |
| 多行计数中途异常 | 更新第 n 项后抛异常 | 整个 T5 回滚，返回失败，不存在半批计数 |
| 向量写入后、成功事务提交前故障 | T3 中间抛异常或进程终止 | 文档和任务共同回滚；重启后恢复，不能半就绪 |
| 提交完成、尚未入队 | 在提交后钩子处停进程 | 同一 H2 文件重启后 QUEUED 被补投 |
| 领取完成、CPU 计算中 | 测试握手确认 RUNNING 后终止进程 | 下次启动有界恢复，attemptCount 不因纯入队增加 |
| 成功提交、内存集合未清理 | 提交后握手，再终止进程 | 重启保持 SUCCEEDED，不重算、不重复完成 |
| 多次处理中崩溃 | 连续进程启动/终止 | 第 3 次执行中断后下次启动为 FAILED，原因可查询 |
| 队列与积压过载 | 小阈值、暂停 worker、并发提交 | 接收数不超过阈值；已接收任务不丢；拒收无孤儿记录 |
| 搜索与失效/发布竞争 | 闩锁控制读写锁先后 | 两种顺序都满足 D11；无效状态不会被发布覆盖 |
| 数据库临时冲突/持续不可用/提交不明 | 可控事务结果及异常注入 | 已确认回滚才有限重试；持续故障降级不直接退出；不明结果先核对，T5 不盲重放；DB 重试不加 attemptCount |
| 检索整体超时/取消 | 在 CPU、扫描、计数前后设置检查点 | 未提交事务回滚；最终释放锁和许可；已提交/结果不明不谎称回滚 |
| 优雅停止/强制停止 | 分别正常关停与终止 Java 子进程 | 前者等待或中断；后者按账本恢复，终态不回退 |

进程级测试通过测试工具拉起真实 Java 子进程，给它独立临时 H2 文件目录；用就绪/检查点信号确定终止窗口，再重用同一目录启动。不得操作开发者正在使用的数据库，不拿同 JVM 内存测试替代这组证据。测试自己管理创建的子进程并清理资源。

P5-B 可选做一组有限的性能观察：记录 Java 版本、机器 CPU、worker/队列/模拟轮数、语料数量/平均长度、并发数，以及提交/检索延迟和完成吞吐。建议先 1,000 篇，再按机器条件试 10,000 篇；不把建议规模当必须达标数字。解释慢在 CPU、全量扫描、锁等待还是计数行锁；不为了漂亮结果改掉一致性语义。

完成条件：核心验收有实测支撑，故障失败后修复并回归；增强验证逐项标注已做/未做及限制，不以“线程安全”字样代替证据。

## 5. Git 节奏与最终停止条件

1. 已先提交三份修订后的设计文档，再开展 P1；P1、P2 已各自提交。
2. P3 依用户后续授权单独提交。每次提交前看 diff、运行对应必要验证，不能混入数据库文件和日志。
3. 发现实际缺陷时保留原因、失败测试和修复说明；不故意制造错误以增加历史，也不伪造之前不存在的 commit 时间。
4. Git 提交说明应对应已完成行为，避免把“仅设计”写成“已支持”。不要在尚未通过时写“所有测试通过”。
5. 当前轮完成条件：P4、核心 P5、P6 分别实现、验证并提交；从干净目录构建、测试和启动验证交付可复现。暂缓服务器部署、万篇压测、穷举崩溃窗口和可选重构。
